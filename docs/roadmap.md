# barista-skill 战略路线图 v3.1 – v3.4

> 战略顾问会话产出 · 2026-07-26
> 状态：**已校准 · 落地中**（决策：阶段粒度维持 / 架构先行 / 编排层新增工具 / 落成 GitHub Issues+Milestones）

## 一、战略锚点（已与用户确认）

| 维度 | 结论 |
|------|------|
| 一号用户 | 咖啡爱好者 / 家庭冲煮玩家（重心）；职业咖啡师 / SCA·Q-Grader 备考者 = 向上延展覆盖层 |
| 使用场景优先级 | A 给参数 > B 救风味 > C 陪练进阶 > 特调（末位） |
| A 场景短板 | 个性化 + 覆盖度 + 闭环（三块都要） |
| B 场景短板 | 识别引导 + 结合上下文反推 + 与 A 闭环打通 + 知识覆盖（都要）；**最痛 = 识别引导** |
| 架构决策 | **混合**：skill 定义 `user_profile` / `brew_session` schema + 会话协议；宿主 agent 持有状态并传参；工具消费上下文。skill 自身不加持久存储 |
| 主护城河 | **闭环教练体验**（A+B+C 串成私人陪练）；准确性 / SCA 深度 / agent 原生为三大支撑柱 |
| 历史账 | 特调在 v2.x 投入重（Jimmy ASR、online_craft_recipes），现排末位 → **冻结新投入，维护态** |

### 关键串联判断

C（感官训练）在"使用频率"排第三，但在"价值链条"是上游——A 的闭环要求用户能自评杯测，B 的识别引导要求用户能命名风味，二者能力都来自感官训练。排优先级时按价值链条加权，而非仅按频率。

## 二、阶段规划（追踪：GitHub Milestones + Issues）

### Phase 0 — 混合架构基座（目标版本 v3.1.0）

**目标**：让 A/B 主工具能消费用户上下文，定义闭环所需的结构契约。

交付物：
1. 设计 `user_profile` schema：设备（磨豆机型号 / 冲煮器具 / 手冲壶）、水质（TDS / 水源）、口味偏好、技能等级、常喝豆类型
2. 设计 `brew_session` schema：豆信息、冲煮法、采用参数、自评分（aroma / acid / sweet / body / aftertaste 等）、文字反馈
3. 编写 `references/brewing-coach-protocol.md`：定义宿主在哪些节点采集 / 回传上下文、闭环的对话结构（start → params → brew → eval → diagnose → tune）
4. 改造 `get_recipe` / `get_parameters_guide`：新增可选 `user_context` 参数，按设备 / 水质 / 手法个性化输出
5. 改造 `diagnose_flavor`：新增可选 `user_context` + `guided` 模式，先做识别引导再给原因

- **里程碑**：A/B 主工具消费上下文；协议文档发布；self_check + pytest 全绿
- **指标**：A/B 主工具上下文参数覆盖率 = 100%；协议文档 reviewer 通过；测试门禁零回归

### Phase 1 — 识别引导（目标版本 v3.2.0）【B 最痛】

**目标**：用户从"好酸"能走到"这是未萃取尖酸 → 原因 → 改法"。

交付物：
1. 基于现有 `coffee_chemistry_sensory.json` + 风味轮 + 感官训练，构建"风味辨识引导树"：
   - 酸：尖酸 / 醋酸 / 未萃取酸
   - 苦：萃取过度 / 焦苦 / 豆疵苦
   - 涩：未萃取 / 水质 / 豆源
   - 甜缺失 / 醇厚度不足 等
2. 新增 `identify_flavor` 工具（或 `diagnose_flavor` 的 guided 模式升级）：输入模糊描述 → 输出判别问题序列 → 定位子类 → 关联原因
3. 知识覆盖补缺：木质 / 橡胶 / 发酵过度 / 药感 等异味进库

- **里程碑**：top 12 高频风味抱怨均有判别路径；识别引导可独立跑通
- **指标**：判别路径覆盖 ≥ 12 类；每个子类含 ≥ 2 个判别问题；pytest 用例（正常 + 边界）≥ 每工具 2

### Phase 2 — 覆盖度扩展（目标版本 v3.3.0）【A 覆盖度】

**目标**：参数矩阵覆盖更多豆子 / 器具，减少"查不到"的空档。

交付物：
1. 扩展豆子产区 / 处理法数据（用户高频但当前缺的：哥伦比亚 / 危地马拉 / 厌氧处理等）
2. 扩展器具参数（不同手冲壶流速特征、法压 / 爱乐压变体、摩卡壶）
3. 充实 `get_parameters_guide` 的调参矩阵维度

- **里程碑**：数据基数提升；EXPECTED_CARDINALITY 同步
- **指标**：新增豆子条目 ≥ 15；新增器具 ≥ 6；测试集空档命中率显著下降

### Phase 3 — 闭环打通（目标版本 v3.4.0）【主护城河】

**目标**：A→B→C 串成可迭代的私人陪练回路。

交付物：
1. 新增轻量编排层：`start_brew_session`（建会话）/ `log_brew_result`（记自评分 + 反馈）/ `next_step`（据历史给下一步：再调 / 诊断 / 进阶）— 工具数 20 → 23
2. 协议落地：宿主在 start → params → brew → eval → diagnose → tune 各节点传递 `brew_session`
3. C 衔接：当用户连续 N 次稳定，触发"想系统学感官 / SCA？"进阶入口（调用现有 `get_sca_path` / `get_qgrader_study_plan`）

- **里程碑**：端到端回路可在脚本化场景跑通（A 给参 → 自审 → B 诊断 → 再调）
- **指标**：回路完成率（脚本化场景）≥ 80%；跨轮次个性化命中（参数随历史调整）验证通过

## 三、跨阶段常驻事项

- **准确性**：所有新增数据带核实出处（延续"八荣八耻"）；`sca_official_sources.json` 持续补全
- **SCA/Q 维护**：v3.0.0 内容随官方更新维护，不扩张新模块
- **en 镜像债**：6 篇新 references 仍 mono（allowed_mono 豁免）；排期 v3.5 补译，恢复双语传统
- **特调冻结**：维护态，不新增数据；如实际用量低可降级为纯索引

## 四、资源分配建议（按优先级压资源）

| 优先级 | 阶段 | 占比 | 理由 |
|--------|------|------|------|
| 1 | Phase 0 + 3（架构 + 闭环） | ~40% | 主护城河，最高杠杆 |
| 2 | Phase 1（识别引导） | ~25% | B 最痛，且是闭环的入口能力 |

| 4 | 常驻（准确性 / en 债 / 特调维护） | ~15% | 维护基线，不抢主线 |
